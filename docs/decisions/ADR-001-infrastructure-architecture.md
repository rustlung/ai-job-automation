# ADR-001: Разделение инфраструктуры на on-demand orchestration и compute worker

Дата: 2026-07-18

Статус: Accepted

## Контекст

Проект AI Automation Lab создается как домашняя инфраструктура для
автоматизации поиска и анализа вакансий.

Изначально рассматривался вариант запуска всех компонентов на одном
сервере, однако доступное железо имеет ограничения:

-   homeserver --- старый ноутбук с Ubuntu Server 24.04 и ограниченными
    ресурсами;
-   тяжелые AI-задачи требуют GPU;
-   часть интеграций зависит от VPN;
-   постоянная работа всех сервисов не требуется.

## Решение

Архитектура разделяется на два слоя:

1.  Orchestration layer.
2.  Compute layer.

## Homeserver

Роль:

On-demand orchestration layer.

Ответственность:

-   n8n;
-   управление workflow;
-   хранение состояния;
-   база данных;
-   легкие сервисы.

Homeserver не должен выполнять тяжелые вычислительные задачи.

Режим работы:

-   включается при необходимости;
-   выключается после завершения работы.

## Worker laptop

Роль:

On-demand compute layer.

ОС:

Windows 11.

Оборудование:

-   NVIDIA RTX 3060 Laptop;
-   16 GB RAM.

Ответственность:

-   локальная LLM через Ollama;
-   тяжелый парсинг;
-   браузерная автоматизация;
-   VPN-зависимые сервисы;
-   экспериментальные сервисы.

Worker не работает постоянно.

## Управление инфраструктурой

Включение и выключение серверов не является частью workflow.

Отдельный слой управления:

-   Wake-on-LAN;
-   SSH;
-   скрипты запуска/остановки.

Правильный порядок:

Пользователь включает инфраструктуру.

↓

Проверяет готовность.

↓

Запускает workflow.

## Рассмотренные альтернативы

### Все сервисы на homeserver

Отклонено.

Причины:

-   недостаточно ресурсов;
-   невозможно комфортно использовать локальную LLM;
-   усложнение поддержки.

### Основной ПК как единственный worker

Отклонено как основной вариант.

Причины:

-   отсутствие мобильности;
-   ПК используется для разработки;
-   нагрузка может мешать основной работе.

Допускается как резервный AI worker.

### Полностью автоматическое включение worker через n8n

Отклонено.

Причины:

-   избыточная сложность;
-   отсутствие необходимости;
-   смешивание управления инфраструктурой и бизнес-процессов.

## Последствия решения

Плюсы:

-   гибкость;
-   экономия ресурсов;
-   возможность использовать разное железо;
-   четкое разделение ответственности.

Минусы:

-   требуется управление состоянием узлов;
-   требуется проверка доступности worker;
-   увеличивается количество компонентов.

## Будущее развитие

Возможное развитие:

замена n8n на собственный orchestration engine при сохранении
worker-сервисов.
